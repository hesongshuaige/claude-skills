# 发言稿写作引擎（fyg）

## 定位

本 skill 用来把正式发言类任务拆成可执行、可检查、可复盘的写作流程。它适合政府、国企、事业单位、招商投资、合作会见、人事推荐等质量敏感、口径敏感、容易写偏的材料。

核心原则：

**先讲清场景，再确认依据，再定义产出，再设置护栏，再安排验收，最后复盘沉淀。**

小任务用简版，大任务用完整版：

| 任务类型 | 使用深度 |
|---------|---------|
| 润色一句话、改标题、压缩字数 | 简版：产出要求 + 风格标准 + 自检 |
| 常规发言稿、会见发言、推荐材料 | 标准版：Context + Source + Procedure + Harness + Verification |
| 对外发布、涉投资/基金/招商/组织人事、领导正式场合、多方协同反复使用 | 完整版：六层全用，并加入 Iteration |

## 触发条件

用户说以下任一关键词时加载本 skill：
**会议发言类**：发言稿 / 讲话稿 / 座谈发言 / 座谈会发言稿 / 汇报材料 / 交流发言 / 纪检座谈会 / 招商座谈会 / 改革座谈会 / 党建座谈会 / 补充发言
**会见企业类**：会见发言 / 会见讲话稿 / 企业会见 / 合作方会见 / 招商会见 / 婉拒 / 暂缓 / 推掉 / 接待发言 / 拜访发言 / 合作交流发言
**推荐材料类**：干部推荐材料 / 换届推荐 / 提拔建议 / 推荐人选 / 配备建议
**迭代反馈类**：改好的稿子 / 领导改稿 / 同事改稿 / 修改前后对比 / 沉淀一下 / 更新口径 / 以后按这个写

## 不要用本 skill 的场景

- 写初研报告/投资研判 → 用 cybg
- 内部工作部署/向下属派活 → 用 internal-work-deployment-speech（本 skill 专注对外/向上的正式发言）
- 排版/生成 Word 文档 → 用 pb（本 skill 专注内容策略，不做排版）
- 绩效考核方案 → 用 performance-review-diagnosis
- 日常公文（通知/请示/函）→ 非本 skill 覆盖范围

## 总执行流程（六层）

### 1. Context：先定场景和边界

动笔前先确认：

- 发言人身份、单位层级、职务权限、分管范围
- 场合类型：座谈、正式汇报、会见企业、招商接待、组织推荐等
- 听众对象：上级、平级、下级、企业、组织部门、合作方
- 发言顺序：先讲、回应、补充、总结、自由发言
- 核心诉求：展示成绩、回应诉求、争取支持、稳妥表态、推荐人选
- 禁区边界：不能说什么、不能承诺什么、哪些信息未公开

### 2. Source：再确认依据和素材

素材优先级按以下顺序处理：

1. 用户明确给出的正式材料、领导口径、会议通知、项目台账、履历、数据表
2. 公司/单位内部已确认材料、会议纪要、正式报告、公开披露文件
3. 官方政策、政府网站、公告、权威新闻
4. 第三方报告、媒体报道、AI 生成内容、口头信息

Source 规则：

- 正式数据必须和用户给出的材料一致，不得为了文采编数据。
- 涉及投资金额、基金产品、招商项目、干部履历、职务任免、未公开项目时，必须提示用户核实公开披露权限。
- 材料冲突时，以用户明确指定的正式口径为准；未指定时先指出冲突，再给可替换写法。
- AI 生成内容只能作为参考，不得当作事实来源。
- 信息不足时可以合理假设，但必须标注“以下按某某情况假设”。

### 3. Procedure：把意图变成动作

**第零步：问清楚再动手（必须执行，不得跳过）**

执行下方「先了解你是谁」问卷。"你是谁"和"什么场合"两条必须确认，缺一条不能动笔。其余问题用户回答不了的，Agent 给合理假设（标注出来），继续写。

**第一步：场景路由（硬编码，不靠模型猜）**

根据用户意图自动路由到对应 reference。触发词判定优先，模糊时强制追问。如果用户一句话混了两个场景（如「帮我写个座谈发言，顺便理婉拒口径」），拆成两个独立任务分别路由，不要合并处理：

| 触发词 | 路由到 | 说明 |
|--------|--------|------|
| 座谈 / 交流 / 研讨 / 纪检 / 汇报发言 / 补充发言 | `references/会议发言稿方法.md` | 按铁律零做角色定位分析 |
| 会见 / 招商 / 接待 / 拜访 / 婉拒 / 暂缓 / 推掉 | `references/会见企业发言方法.md` | 先确认四种姿态 |
| 推荐 / 提拔 / 换届 / 配备建议 | `references/干部推荐材料方法.md` | — |
| 改好稿 / 领导改稿 / 同事改稿 / 沉淀经验 | `references/迭代反馈协议.md` | — |

路由后进入对应 reference 执行场景特定流程。

**通用步骤：**

1. **第零步（前置）**：执行「先了解你是谁」问卷，确认身份和场合。
2. 路由到场景 → 执行场景特定流程（role analysis / 姿态确认等）。
3. 整理 Source：列出已确认事实、待确认事实、不能写或需弱化的信息。
4. 确定结构：选用对应 reference 的标准结构，并按发言顺序调整重点。
5. 起草：先给文字稿，不默认做 Word 排版。排版统一交给 `pb` 技能。
6. 自检：先执行对应 reference 的「写作中必守（Harness）」，再执行「⚡交付前必检（Verification）」，最后按本 skill 通用清单逐项检查。任一条未通过 → 标注缺陷、返回修改、不交付。信息不足无法检查的项 → 标注"待用户确认"后继续。
7. 交付：必要时列出"需用户确认的事实/口径"。

如果用户发来"AI 初稿 + 人工改稿"或"改好的最终稿"，不要继续重写，先进入 `references/迭代反馈协议.md`。

**附：「先了解你是谁」问卷**

Agent 必须先搞清以下信息。用户没给的主动问，给了的确认一遍。不问清楚就写 = 张冠李戴。

##### 通用必问（三类场景都适用）

1. **你是谁**：确切职务，不要猜
2. **你单位**：政府/国企/事业单位？什么级别？大概多少人？
3. **什么场合**：座谈会？正式汇报？会见企业？你的发言顺序是第几个？
4. **听众/对象是谁**：上级领导？平级同行？下级？合作企业？
5. **核心诉求**：这次发言你最想传达什么？争取什么？回避什么？
6. **依据材料**：有没有会议通知、领导口径、正式报告、项目台账、履历、合作背景、历史稿件？
7. **使用边界**：是否对外发布？是否涉及投资收益、基金宣传、未公开项目、干部任免、敏感数据？

##### 场景特定追问

| 场景 | 额外必问 |
|------|---------|
| 会见企业 | 合作背景是什么？投了多少钱？对方落地了什么？对方这次想要什么（资金/政策/资源）？你希望对方接下来做什么？ |
| 推荐材料 | 推荐谁担任什么职务？班子现状怎样？被推荐人的完整履历和硬业绩？口头汇报材料还是正式行文？ |
| 座谈发言 | 有没有拿到其他人的发言材料（特别是领导的）？有没有特定要回避的敏感话题？ |

**信息不足时的处理：** "你是谁"和"什么场合"两条必须确认，缺一条不能动笔。其余问题用户回答不了的，Agent 给合理假设（标注出来），继续写。

**对人协同任务的改写：** 如果用户不是要 Agent 直接写稿，而是要给下属/部门布置发言材料任务，则改用管理版表达：背景目标、牵头人、配合方、依据材料、交付物、截止时间、质量标准、验收人、卡点升级机制。

### 4. Harness：过程护栏

写作过程中必须遵守：

- 不承诺收益，不暗示保本，不夸大投资业绩。
- 不披露未公开项目、未公开基金安排、未确认干部任免信息。
- 不用"稳赚""保本""高收益""一定落地""保证解决"等绝对化表达。
- 不编造领导讲话、政策依据、会议背景、项目数据、履历业绩。
- 不把座谈发言写成正式报告，不把企业会见写成上下级训话，不把推荐材料写成个人先进事迹。
- 每个场景动笔前必须执行对应 reference 的「写作中必守（Harness）」区块中的约束。这些约束是场景特定铁律，不能因为通用框架而稀释。
- 排版统一交给 `pb` 技能。fyg 专注内容策略，不做字体/字号/页边距等格式操作。
- 不机械套六层。简单修改只保留必要的背景、产出和自检。
- Harness 是写作过程约束（写作中遵守）；Verification 是交付前验收（写完后检查）。两者已拆分到 reference 的独立区块，不要混在一起。

### 5. Verification：交付前验收

交付前必须检查：

- Context 对：身份、场合、听众、发言顺序、诉求没有错位。
- Source 对：所有具体事实、数字、人名、职务、项目名都有来源或已标注待确认。
- 结构对：匹配会议发言、干部推荐、企业会见的对应结构。
- 风险对：没有越权承诺、收益承诺、未公开信息、过度表态。
- 语言对：读出来像真人发言，短句多，空话少，有可记住的判断或表态。
- 交付对：如果信息不足，必须把假设和待确认项列出来。
- 压力对：修改 fyg 后应跑 `references/压力场景库.md` 中的场景验证不退化。

### 6. Iteration：复盘沉淀

当用户反馈“这版好/不好”“领导改了”“以后都按这个口径”时，Agent 应主动提炼：

- 哪些表达、结构、口径可沉淀为模板
- 哪些禁忌、领导偏好、单位口径要补入本 skill 或参考文件
- 哪些场景需要新增案例或拆成单独 reference
- 是否需要把最终版和修改理由形成下一次可复用的写作规则

迭代分三档：

| 档位 | 触发 | 处理 |
|------|------|------|
| 记录 | 用户只发改好稿，未要求更新技能 | 输出“迭代反馈卡”，不改文件 |
| 建议沉淀 | 用户说“帮我总结经验/以后怎么写” | 提炼规则，建议放入哪个 reference |
| 写回技能 | 用户明确说“沉淀到技能/更新 fyg/写入规则”，或明确指出哪些内容要迭代 | 修改对应 reference，保留来源说明、适用边界和验证结果 |

不要在一次性小改里强行复盘；重复发生、质量敏感、返工明显时才主动建议沉淀。一次出现的默认放案例，三次以上重复出现的才由 Agent 主动建议升级为通用规则；但用户已经完成分析并明确指定要迭代的内容时，可以直接写入，并标注为"用户指定规则"。

## 场景方法文件

根据用户意图读取对应 reference。不要一次性加载所有参考文件。

| 场景 | 读取文件 | 核心检查 |
|------|---------|---------|
| 座谈会发言、汇报发言、交流发言 | `references/会议发言稿方法.md` | 角色定位三步分析；三条做法是否有人名+机制；困惑段是否用"请教"包装且有诉求；多企业座谈会是否回应了所有董事长 |
| 换届推荐、提拔建议、人事推荐材料 | `references/干部推荐材料方法.md` 和 `references/干部推荐材料模板.md` | 组织需要、硬业绩、落款口径、职务准确、词不过大 |
| 会见企业/合作方、招商接待发言 | `references/会见企业发言方法.md` | 四种姿态已确认；高情商话术已用；拒绝场景是否结论式且不给细节；承诺有边界 |
| 改好稿、领导改稿、同事改稿、沉淀经验 | `references/迭代反馈协议.md` | 修改原因、可复用规则、适用边界、是否写回技能 |

## 快速自检

任何场景交付前都要过这 7 项：

| # | 检查项 | 通过标准 |
|---|--------|---------|
| 1 | 身份对了吗 | 发言人的职务、权限、分管领域和语气姿态正确 |
| 2 | 场景对了吗 | 座谈、汇报、企业会见、推荐材料没有混用结构 |
| 3 | Source 对了吗 | 具体事实、数据、人名、职务、项目名有依据或标注待确认 |
| 4 | 风险安全吗 | 没有收益承诺、越权承诺、未公开信息、过度表态 |
| 5 | 有真内容吗 | 至少有 2-3 个事实、案例、数据或明确动作 |
| 6 | 像人说的吗 | 读出来顺口，短句多，空话少，收尾有明确表态或下一步 |
| 7 | reference 专项检查做了吗 | 对应场景的「写作中必守」和「⚡交付前必检」已逐项通过 |
