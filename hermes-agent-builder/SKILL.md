# Hermes Agent Builder

## 目标

把一个模糊的“帮我做智能体”请求，变成可运行、可验收、可回滚、可复用的 Hermes Agent（智能体框架实例）。保持当前 Agent开发 的完整方法：先理解工作，再建档，再实现，再用真实样例验收。

**不要把技能当成权限隔离。** 技能是流程规则；真正的密钥隔离、删除硬拦截、运行账号和服务边界，必须由 Hermes 运行时、操作系统权限和服务配置共同保证。未验证的边界不得声称已经成立。

## 不可违背的规则

1. 先读现有配置、最新岗位卡和已有成果物，再动手；不要只凭聊天记忆。
2. 已知目标可跳过重复盘点；未知目标才进入澄清。澄清时每轮只问一个问题，答完先用不超过15个中文字符总结。
3. 任何删除、覆盖、清空、撤回、停服务，都要在当次明确说明对象、影响和回滚，并取得批准；外部消息、改数据、长期定时只有在对象、范围和内容已被明确批准时才能自动执行，超出范围必须重新确认；“顺便清理”“越快越好”不等于批准。
4. 只允许当前用户使用时，配置用户白名单；群聊还要配置明确群规则和是否必须提及。未知群号不能假装已限制到某个群。
5. 不输出密钥、应用凭证、用户编号、服务器密码或授权状态原文；环境文件权限不宽于600，建议严格为600。
6. 不用全局或会话级免审批模式绕过单次删除审批；不允许智能体自改守卫、启用依据或运行入口。
7. 每次写入后回读核验；每次声称完成前核对运行状态、指纹、权限和目标行为。
8. 失败时停在安全状态，说明证据、未完成项和下一步；不要用“应该可以”代替验证。

## 总流程

### 0. 判断是否需要澄清

- 目标、输入、输出、权限、验收都已在最新岗位卡中明确：直接进入复用流程。
- 任一关键项不明确：进入“需求澄清”，不要因用户催促而跳过。

### 1. 需求澄清与优先级

未知目标按五轮做，每轮一个问题：

1. 重复性：这件事多久重复一次，是否值得做成智能体？
2. 输入稳定性：输入从哪里来，格式是否固定？
3. 规则清晰度：哪些判断必须一致，哪些可由人决定？
4. 输出可验收性：结果长什么样，放在哪里，怎样算成功？
5. 人工兜底：不确定、失败、敏感动作由谁确认？

每轮回答后先总结，再生成重复工作卡。五项评分：重复、输入稳定、规则清晰、输出可测、人工兜底。4—5分优先做；2—3分先缩小范围并加检查；0—1分暂缓。

用一句话固定岗位：`输入 X，经由动作 Y，产出结果 Z`。没有 X、Y、Z 就不能进入实现。

### 2. 岗位卡访谈

按六轮、每轮一个问题确认：

1. 输入：来源、格式、最小示例。
2. 过程：3—8个动作和顺序。
3. 输出：位置、格式、命名和是否需要版本。
4. 验收：成功、失败、部分成功的判定。
5. 人工介入：哪些节点必须停下来问人。
6. 禁止事项：绝不能做什么。

把回答整理成岗位卡，问“哪里需要调整？”；用户未明确说“可以/确认”前，标为草稿，不当作最终规则。

### 3. 成果物与知识库

优先写入用户指定的飞书知识库，不把本机文件当长期事实来源。建议建立一个成果物根节点，并固定以下页面：

| 页面 | 内容 |
|---|---|
| 01-岗位卡 | 已确认的职责、输入、输出、边界 |
| 02-工作流卡片 | 步骤、工具、判断、失败和人工兜底 |
| 03-流程图 | 触发、处理、至少两个判断节点、结束 |
| 04-Profile | 可执行的角色与质量规则 |
| 05-测试记录 | 三个样例、证据、问题、修复和回归 |
| 06-使用说明 | 怎么触发、怎么审核、怎么恢复 |
| README | 页面索引、版本和维护约定 |

写入前先读最新页面；覆盖已有内容前说明范围并取得批准；写入后回读标题、正文和版本。只保留用户确认的最终规则，草稿要标注状态。

### 4. 人工流程与隐藏判断

先把人工流程写成5—12步，补齐每步的输入、动作、输出、耗时和工具。再逐步问“你通常怎么判断？”：

- 把判断分为 `MUST`（必须）、`SHOULD`（建议）、`MAY`（可选）。
- 明确触发器、数据流、幂等键、成功条件、失败条件、重试、回滚和人工兜底。
- 用流程图表达分支；至少有两个真实判断节点，不要用装饰性的方框冒充判断。

### 5. Profile（智能体档案）设计

Profile 必须包含：身份与目标、输入与来源、处理步骤、输出位置与格式、质量检查、自检、异常处理、人工兜底、禁止事项、版本和回滚。

按任务类型补检查：

- 内容/文档：事实、结构、语气、引用、版本。
- 录音/逐字稿：原文保留、错别字标记、任务/负责人/截止时间、疑点确认。
- 表格/办公：字段、公式、重复、空值、写入范围。
- 客服/外部沟通：身份、收件人、语气、敏感信息、发送前确认。
- 数据分析：口径、时间窗、样本、异常、结论证据。
- 自动化：幂等、重试、超时、日志、告警、回滚。
- 知识问答：来源、时效、冲突、引用、未知时拒答。

### 6. 工具、权限与实现

先列工具清单，再逐项验证实际解析结果和权限，不把配置文件里的“想要”当成“已经启用”。每个工具记录：用途、读写能力、外部副作用、审批方式、失败回滚。

对于 Hermes 实例：

1. 创建独立 Profile，不克隆带凭证的旧 Profile。
2. 明确模型、供应商、地址和密钥变量名；只检查键名、权限和调用结果，不输出密钥值。
3. 飞书使用官方长连接；每个 Profile 使用独立应用；私聊用用户白名单，群聊用群白名单加用户白名单。
4. 完整工具权限可以保留，但删除和其他破坏性动作必须逐次批准；浏览器点击、电脑控制、未知外部工具和不透明脚本按可能有副作用处理。
5. 服务先手动运行验证，再安装常驻服务；运行用户、工作目录、解释器和 Profile 必须固定。
6. 改配置、角色规则、服务或凭证前建立可验证回滚点；不影响现有网关。

### 7. 三样例闭环验收

固定三类样例：典型、边界、最重要。每个样例记录：原始输入、实际步骤、工具调用、输出、人工判断、问题和修复。

顺序必须是：运行前基线 → 完整运行 → 人工验收 → 一次只改一条规则 → 用同一样例回归。不要只测“模型说得通”，要证明输入到输出的证据链。

至少验收：

- 私聊本人能触发，非白名单用户被拒绝。
- 群聊只在指定群和指定用户范围内触发，按配置决定是否必须提及。
- 模糊逐字稿会标记疑点并请求确认，不把猜测写成事实。
- 未预先批准范围的删除、覆盖、发送、定时等敏感动作不会静默执行。
- 普通读取、分析和草稿生成不会被不必要地阻塞。

### 8. 长期运行与交付

先手动运行并观察日志，再开启定时。固定输入、输出、身份、工作目录、环境和版本；检查重复定时、重复发送、失败通知、重试上限和恢复路径。交付时提供使用说明、已知限制、测试记录、版本号和回滚方法。

可选制作展示页面，但展示页面不是部署证明，不能替代真实收发、权限和服务验收。

## 典型逐字稿处理

收到领导或员工安排的录音逐字稿时：

1. 保存原文，不静默改写。
2. 标出疑似错别字、人名、日期、数字和语义不完整处。
3. 提取任务、负责人、截止时间、依赖、优先级和来源句子。
4. 把不确定内容放入“待确认”，不要推断成事实。
5. 先给用户审核；确认后再写入飞书知识库或多维表格。
6. 用户修改后记录版本差异，作为后续迭代样本。

## 快速自检表

- [ ] 最新岗位卡已读取，目标不是凭空假设。
- [ ] 输入、动作、输出和验收标准齐全。
- [ ] 权限、白名单、群规则和敏感动作边界已明确。
- [ ] 成果物已写入指定知识库并回读。
- [ ] Profile 包含自检、异常、人工兜底和禁止事项。
- [ ] 典型、边界、重要三样例已运行并记录证据。
- [ ] 服务身份、运行状态、日志、重复和回滚已核验。
- [ ] 未输出秘密；未删除或覆盖未获批准的内容。

## 常见借口与处理

| 借口 | 必须怎么做 |
|---|---|
| “用户催得急，先做再说” | 先问最小关键问题；不依赖该答案的草图可以先做 |
| “这只是小改动，不用测” | 至少做一个边界样例并回读结果 |
| “旧资料反正没用了” | 列清单、说明影响、逐项获批后再处理 |
| “配置写了就说明启用了” | 读取运行时实际工具清单并验证 |
| “模型大概能判断出来” | 把猜测标为待确认，不写成事实 |
| “全放行更方便” | 保留逐次敏感动作审批，不使用全局或会话绕过 |
