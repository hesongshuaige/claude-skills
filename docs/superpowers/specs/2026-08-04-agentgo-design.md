# AgentGo 设计说明

## 1. 目标

创建一个可移植的 `agentgo` 技能，让已经安装 Hermes Agent 的 Claude、Codex 或其他兼容智能体，能够在腾讯云或普通 Linux/Windows 主机上，安全、可验证地创建一个相互隔离的 Hermes 子智能体，并接入独立飞书机器人。

首版采用“半自动向导”：自动完成环境检查、档案创建、文件生成和结果验证；扫码、应用授权、密钥录入及高风险权限变更必须由用户确认。

## 2. 成功标准

使用者下载技能后，应能完成以下闭环：

1. 检查 Hermes、Python、服务管理器及飞书控制工具是否可用。
2. 收集智能体名称、职责、模型、工作目录、飞书使用方式和权限边界。
3. 创建独立 profile，且不复用其他智能体的飞书应用或密钥。
4. 配置模型供应商，并通过一次直连模型测试。
5. 生成可用的 SOUL.md、workspace/AGENTS.md、workspace/README.md 和 workspace/PROJECT.md。
6. 创建或绑定独立飞书应用，启用机器人和长连接。
7. 正确区分机器人权限、应用权限和用户授权。
8. 安装并启动对应 profile 的 Hermes gateway。
9. 完成模型、私聊、群聊、用户知识库及多维表格的分层测试。
10. 生成不含密钥的交接说明和故障排查结果。

## 3. 非目标

- 不自动替用户扫描二维码、确认授权或提升飞书权限。
- 不把 App Secret、模型密钥、服务器密码或用户令牌写入仓库、报告或聊天。
- 不承诺兼容未知的 Hermes 分支或未来命令；执行前必须探测实际版本和帮助信息。
- 不自动迁移旧智能体的定时任务、业务数据或历史记忆。
- 不默认安装新的系统依赖、开放公网端口或使用 root 运行网关。
- 不把“工具已安装”描述成“业务自动化已经完成”。

## 4. 用户和运行环境

主要用户是腾讯云服务器上的 Claude、Codex，以及本机或服务器上的 Hermes Agent。Linux 是主路径，Windows 作为兼容路径。技能必须避免写死用户名、主目录、虚拟环境路径、应用编号和供应商。

运行时先探测以下候选命令：

- PATH 中的 `hermes`。
- Hermes 自带虚拟环境中的 Python 模块入口。
- 用户明确提供的 Hermes 命令。

如果命令或版本与手册不一致，必须先查看本机 `--help`，不能凭记忆继续。

## 6. 主流程

### 阶段一：任务澄清和环境预检

只收集真正影响搭建的内容：

- profile 名称和显示名称。
- 一句话职责、目标用户和主要输入输出。
- 模型供应商、模型名和密钥变量名。
- 飞书仅机器人服务，还是还要控制用户级知识库、文档、云盘和多维表格。
- 私聊允许名单、群聊策略、是否必须提醒机器人。
- 是否需要定时任务及其业务授权边界。

随后检查 Hermes、飞书控制工具、目录权限、同名 profile 和同名服务。若目标已存在，先展示现状，再让用户选择修复、补全或停止；不得覆盖。

### 阶段二：建立隔离档案

使用当前 Hermes 版本支持的 profile create 命令创建档案。创建后确认 profile.yaml、config.yaml、.env、SOUL.md、skills、sessions 和 memories 的实际位置。

强制规则：

- 每个 profile 使用独立配置和飞书应用。
- 不通过 clone 复制飞书凭据。
- .env 只存本档案需要的密钥。
- Linux 下 .env 权限建议为 600。

### 阶段三：配置模型并先行验证

根据实际版本和供应商文档生成最小配置，确保 model、provider、base_url、api_mode 和 key_env 相互一致。密钥由用户在安全终端中录入，智能体不得要求用户把密钥发到聊天。

网关接入之前必须先执行一次不经过网关的短回答测试。失败时停止飞书步骤，先解决模型配置。

### 阶段四：生成人格和项目文件

向导根据用途填充四个模板：

- SOUL.md：长期身份、说话方式、判断原则、真实性约束和权限底线。
- AGENTS.md：项目来源优先级、固定流程、工具规则、幂等、失败恢复和验证标准。
- README.md：面向用户说明“自动运行、按需可用、尚未启用”，附可直接复制的说法。
- PROJECT.md：目标、数据流、文件职责、当前状态和后续启用条件。

config.yaml 的 terminal.cwd 应指向 profile 的 workspace，确保 Hermes 从当前工作目录加载 AGENTS.md。必须检查文件长度；单个上下文文件不超过 Hermes 的 20,000 字符上限。

### 阶段五：创建或绑定飞书机器人

优先使用 Hermes gateway setup 的扫码创应用流程；扫码失败或组织策略禁止时，使用飞书开放平台手动创建。

必须明确展示两条路径：

1. 自动扫码创建：保持设备码注册进程存活，向用户提供有效链接或二维码。
2. 手动创建：创建企业自建应用，开启机器人能力，复制 App ID 和 App Secret 到该 profile 的 .env。

任何注册临时日志若包含 App Secret，验证后立即删除；一旦密钥出现在聊天或普通日志中，按泄露处理并重置。

### 阶段六：权限和授权分层

技能必须把以下三件事分开讲清：

1. 应用权限：在飞书开放平台给当前新应用开通所需权限范围。
2. 机器人身份：用于收发消息及访问机器人有权看到的资源。
3. 用户身份：用于访问用户自己的知识库、多维表格、文档和云盘，需要用户单独授权。

若只需聊天，不强制安装或配置用户授权。若需控制用户级资源，则把 lark-cli 绑定到当前 profile 的新应用，并选择 user-default 身份；调用用户资源时显式使用 `--as user`，不得静默降级为机器人身份。

授权流程采用设备码：生成授权链接和二维码，由用户完成授权，再用设备码轮询结果。链接必须原样传递，不得自行拼接或修改。权限不足时，先判断是应用权限未开还是用户未授权，不能混用处理方式。

### 阶段七：配置并启动消息网关

写入当前 profile 的飞书变量：应用编号、应用密钥、国内或国际域、长连接模式、用户白名单、群聊策略和提醒规则。修改后重启当前 profile 的网关。

先检查是否有其他网关占用同一 App ID；不得启动两个连接同一飞书应用的网关。服务安装、启动和状态检查使用当前系统实际支持的命令；Linux 优先使用用户级 systemd，Windows 使用 Hermes 支持的本机服务方式。

### 阶段八：分层验收

严格按顺序测试：

1. 模型直连测试。
2. 网关状态和日志连接标志。
3. 机器人主动发送一条测试消息。
4. 飞书私聊入站和回复。
5. 群聊提醒模式测试；若配置无需提醒，再单独测试普通群消息。
6. 若启用用户身份，执行身份状态检查。
7. 对一个用户知识库或多维表格进行只读测试。
8. 只有用户明确要求时才做创建或写入测试。

任何一步失败，报告失败层级和影响范围，不得把部分通过描述为全部接通。

### 阶段九：交接

输出不含密钥的交接清单：智能体名称、职责、profile 路径、工作目录、服务名、飞书应用显示名称、允许用户、群聊规则、模型名、已通过测试、未启用能力、常用状态命令和故障日志位置。

## 7. 自动验证脚本

`validate_agent_profile.py` 接收 profile 目录，并执行只读检查：

- 必需文件和目录是否存在。
- config.yaml 是否可解析。
- model/provider/key_env 是否形成完整引用。
- terminal.cwd 是否指向存在的 workspace。
- workspace 下四类项目文件是否齐全。
- 上下文文件是否超过 20,000 字符。
- .env 是否包含必需变量名，但绝不输出值。
- Linux 下 .env 是否过度开放。
- 飞书域、连接模式、群聊策略和提醒值是否合法。
- SOUL.md 与 AGENTS.md 是否误放或加载位置不正确。

脚本以退出码区分通过和失败，并输出修复建议。它不创建 profile、不修改文件、不联网、不读取或打印密钥值。

## 8. 安全门

- 创建应用、扫码授权、增加权限、改变群聊开放范围和写用户资源前，必须获得明确授权。
- 默认设置用户白名单和安全审批模式，不启用 yolo。
- 默认长连接，不要求公网回调地址。
- 不用 root 运行网关。
- 不把凭据提交到 Git、技能目录或生成报告。
- 不把已有应用凭据复制给新 profile。
- 不自动删除旧 profile、旧机器人、旧服务或历史数据。
- 高风险权限采用最小权限原则，并记录用途。

## 9. 已知故障与处理重点

详细表放入 troubleshooting.md，至少覆盖：

- key_env 与 .env 变量名不一致造成 401。
- 独立 profile 未配置模型，静默回退默认供应商。
- 两个网关复用一个 App ID，互相抢占连接。
- 扫码约十分钟过期，或后台进程因标准输入未重定向而退出。
- PowerShell 经 SSH 传中文变成问号，应改用 UTF-8 文件上传。
- 修改配置后未重启对应网关。
- 群聊不回复时，依次检查提醒规则、群策略和允许名单。
- 把机器人权限不足误判成用户未授权，或反过来。
- lark-cli 绑定到了旧应用或错误 profile。
- 授权链接被截断或修改，导致设备码流程失效。
- 日志或聊天泄露密钥后的重置和清理流程。
- AGENTS.md 不在 cwd，导致项目规则未加载。

## 10. 测试策略

在创建技能前先记录无技能时的基线失败，再创建技能并重复测试。

至少包含六个压力场景：

1. 正常创建一个只处理飞书私聊的智能体。
2. 创建需要用户级知识库和多维表格权限的智能体。
3. 用户要求复用旧机器人的 App ID。
4. 用户把密钥直接发在聊天里。
5. 用户要求跳过模型测试并直接启动网关。
6. Windows 控制端向 Linux 服务器传送包含中文的四类文件。

通过标准：技能能让执行者识别身份和权限分层，阻止凭据复用及泄露，生成正确上下文文件，按层验收，并在失败时给出准确排查顺序。

自动测试包括：

- 技能结构和 frontmatter 校验。
- 模板占位符完整性检查。
- 验证脚本的正常、缺文件、错配置和不安全权限用例。
- 敏感信息扫描。
- 使用 skill-creator 的 quick_validate.py。

## 11. 发布方式

在 `hesongshuaige/claude-skills` 仓库中创建独立分支，目录名固定为 `agentgo`。只提交设计文档、技能目录、必要测试和根 README 的索引更新。完成验证后推送远端并创建草稿拉取请求，不直接改写 main。

## 12. 维护规则

以下情况必须复核并更新技能：

- Hermes profile、gateway 或配置格式发生变化。
- 飞书设备码、权限范围或长连接流程发生变化。
- lark-cli 的绑定和授权命令发生变化。
- 新增操作系统支持。
- 压力测试出现新的常见失败。

不兼容改动应升级版本说明；废弃流程明确标注，不静默覆盖。
