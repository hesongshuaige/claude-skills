# 小白 + 专业自查清单

**用法：** 拿到原文后，1-2 分钟内按本清单扫描，标出问题位置。

---

## A. 小白类问题（5 类，扫这类=让小白能看懂）

### A1. 术语没解释

**症状：** 直接抛英文术语，没中文释义或比喻。

**典型例子：**
- ❌ "用 sandbox 限制 Codex 权限"
- ❌ "配置 MCP server"
- ❌ "用 worktree 隔离"
- ❌ "用 subagent 跑独立任务"

**检查方法：** 把每个英文术语在脑子里翻译给完全不懂的朋友听，**说不出来 = 没解释**。

**修复：** 第一次出现术语时用 `术语（中文释义，具体比喻）` 三件套。例如：
- ✅ "sandbox（沙箱，物理上限制 Codex 能干啥不能干啥的"门禁系统"）"
- ✅ "MCP（Model Context Protocol，让 Codex 跟外部工具对接的协议）"
- ✅ "worktree（Git 的"分身"功能，让每个 agent 在自己独立目录里干活）"

### A2. 没比喻/故事引入

**症状：** 上来就讲规则、讲概念、讲"是什么"。

**典型例子：**
- ❌ "AGENTS.md 是一个 Markdown 文件，用于配置 Codex 行为。"
- ❌ "本章将介绍 Codex 的工作流。"

**检查方法：** 文章前 3 段**有没有比喻/故事/场景**？没有 = 上来就讲规则。

**修复：** 用"想象你招了 X""强力实习生""自助餐""门禁系统"等具体比喻，**别用"本章""本节""我们将"这种学术腔**。

### A3. 抽象无落地

**症状：** 讲了很多"应该做 X"，但没说"做到啥样算对"。

**典型例子：**
- ❌ "做好边界控制"
- ❌ "Codex 需要有清晰的上下文"
- ❌ "提示词要写好"

**检查方法：** 每个抽象建议后面**有没有可量化的标准**（数字、命令、文件名、参数）？

**修复：** 把抽象建议改成可验证标准。例如：
- ✅ "用 `pnpm test -- src/auth/login.test.ts` 跑特定测试"
- ✅ "AGENTS.md 至少 5 个模块，每个模块都有真实可跑命令"
- ✅ "提示词 5 字段：目标 / 范围 / 上下文 / 验收标准 / 约束"

### A4. 缺对比/反例

**症状：** 只讲"应该 X"，没讲"不应该 Y"或"X 跟 Y 区别"。

**典型例子：**
- ❌ "用 AGENTS.md 告诉 Codex 项目规矩"（没说跟 README 区别）
- ❌ "跑测试前先写测试"（没说为啥、不写会怎样）

**检查方法：** 每个"应该"后面**有没有"不应该"或"区别"**？

**修复：** 加对比表（"X vs Y"），加反例（"❌ 反例：..."）。

### A5. 没检查清单

**症状：** 文章结尾只有"完"或一句总结，没有可勾选的自查清单。

**典型例子：**
- ❌ 结尾："希望对你有帮助。"
- ❌ 结尾："按上面做就行。"

**检查方法：** 结尾**有没有 5+ 条可勾选的 `- [ ]` 列表**？

**修复：** 加 8 条具体到文件名/命令/参数的自查清单。

## B. 专业类问题（5 类，扫这类=让专业可信）

### B1. 命令像占位符

**症状：** 命令里带 `...` 或 `<placeholder>`，小白根本跑不通。

**典型例子：**
- ❌ `pnpm test ...`
- ❌ `prisma migrate dev --name <name>`
- ❌ `git checkout ...`

**检查方法：** 拿每个命令**自己手敲一遍**，能跑通 = 通过；跑不通 = 占位符。

**修复：** 给完整命令 + 真实参数 + 真实场景。例如：
- ✅ `pnpm test -- src/auth/login.test.ts`
- ✅ `pnpm prisma migrate dev --name add_user_email_index`
- ✅ `git checkout -b feature/login-validation`

### B2. 绝对化表达

**症状：** "不许""绝对不要""必须 X" 这种过强的措辞。

**典型例子：**
- ❌ "不许 push 到 main 分支"
- ❌ "绝对不要改 .env 文件"
- ❌ "必须用 TypeScript"

**检查方法：** 找"不许""绝对""必须"等强词，**判断是不是真硬规则**。

**修复：**
- 硬规则（涉及安全/合规）→ 保留"必须/不许"
- 软建议（风格/偏好）→ 软化为"建议/尽量/不直接"

例如：
- ✅ "不直接 push 到 main 分支（要走 PR）"
- ✅ "建议不要改 .env 文件，除非任务明确要求"
- ✅ "建议用 TypeScript，除非项目历史是 JavaScript"

### B3. 工具名/版本错误

**症状：** 举例用的工具版本跟实际命令不一致。

**典型例子：**
- ❌ 用 GPT-4 举例但写 GPT-5 的 API
- ❌ `prisma@4` 的命令但写到 `prisma@5` 文档里
- ❌ macOS 路径 `/Users/xxx` 但用户是 Linux

**检查方法：** 关键工具版本、命令、路径**跟官方最新文档对一下**。

**修复：** 用主流稳定版本，路径用相对路径或 `$HOME` 替代绝对路径。

### B4. 配置路径错误

**症状：** 配置路径跟用户系统/工具链不匹配。

**典型例子：**
- ❌ `~/.claude/skills/` 但用户用 Codex
- ❌ `/etc/codex/config.toml` 但用户是个人项目
- ❌ 写到 `package.json` 但用户用 `pyproject.toml`

**检查方法：** 配置路径**跟主流用户场景对一下**。

**修复：** 用最常见的路径（Codex 用户的 `~/.codex/`、Node.js 项目的 `package.json`、Python 项目的 `pyproject.toml`）。

### B5. 缺失败案例

**症状：** 只讲 happy path，没讲翻车怎么处理。

**典型例子：**
- ❌ "用 Codex 修 bug：定位 → 修复 → 验证"（没说定位错了咋办）
- ❌ "Codex 改完代码后跑测试"（没说测试挂了咋办）

**检查方法：** 每个流程**有没有"如果 X 失败就 Y"的分支**？

**修复：** 加纠偏提示词（"先停一下，请重新对照..."）、加反例库。
