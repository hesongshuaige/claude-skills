# 升级版反例库

**用法：** 跑完一篇升级后，对照本清单自检。如果你升级后的版本命中了任何"反例"，立即修。

---

## 反例 1：保留原文绝对化词，没软化

**症状：** 升级版里直接抄了原文的"避免 / 绝对 / 必须 / 一定"。

**真实案例：**
- ❌ 原文："RAG 可以**避免**幻觉" → 升级版照抄
- ❌ 原文："代码必须加注释" → 升级版照抄
- ❌ 原文："**绝对不要**改 .env" → 升级版照抄

**正确做法：**

| 原文强度 | 升级版处理 |
|----------|------------|
| 硬规则（涉及安全 / 合规） | 保留"必须 / 不许"，但加"为啥"和"咋办" |
| 软建议（风格 / 偏好） | 软化为"建议 / 尽量 / 不直接" |
| 绝对化（"避免 / 一定 / 永远"） | 软化为"降低 / 通常 / 多数情况下" |

- ✅ "RAG 能**降低**幻觉（但不能 100% 消除）"
- ✅ "**建议**加注释（除非是显而易见的代码）"
- ✅ "**不直接**改 .env，除非任务明确要求"

**兜底：** 如果升级版里出现了原文的"绝对化词"，要么软化、要么加一段"软化提醒"补充限制条件。

## 反例 2：故事开场太长（> 5 句）

**症状：** 故事开场写了 6+ 句比喻 / 场景 / 历史背景才进主题。

**真实案例：**
- ❌ "想象你招了一个新员工。**这员工很能干，但不熟悉你们公司。** 第一天上班，他最怕啥？**不是干活难，是不知道规矩。** 你跟 Codex 每次对话开头说'先读 README'——太累也容易忘。**更好的办法：在项目根目录放一个叫 AGENTS.md 的文件，让 Codex 第一次进项目就自动读。** **说白了：AGENTS.md 就是给 Codex 看的员工手册。** 有了它，Codex 不用你每次提醒也能照规矩办事。**而且它能在 30 秒内读懂项目结构。**"

**正确做法：** 故事开场 3-5 句为佳。

- ✅ 3 句："想象你招了一个新员工。这员工很能干，但不熟悉你们公司。**第一天上班，他最怕啥？不是干活难，是不知道规矩。**"
- 主体内容放"## 啥是 X？"段

**为啥：** 故事开场太长 = 读者等得不耐烦就跳走了。**3 句引起共鸣就够**，细节留到正文。

## 反例 3：检查清单写空话

**症状：** 检查清单是抽象建议，不能勾选 / 不能验证。

**真实案例：**
- ❌ "- [ ] 做好准备工作"
- ❌ "- [ ] 关注用户体验"
- ❌ "- [ ] 写好代码"
- ❌ "- [ ] 性能良好"

**正确做法：** 每条都"具体到可勾选"——文件名、命令、参数、数字。

- ✅ "- [ ] 项目根目录有 `AGENTS.md`"
- ✅ "- [ ] AGENTS.md 里有 5 个完整模块（项目概览 / 常用命令 / 代码规范 / 安全边界 / 完成标准）"
- ✅ "- [ ] 5 个模块里都有真实可运行的命令（不是 `...` 占位符）"
- ✅ "- [ ] 跑 `pnpm test -- src/auth/login.test.ts` 能 100% 通过"

**判断标准：** 把每条检查项拿给一个不懂的人看，**他能不能在 30 秒内判断"过 / 不过"**？不能 = 空话。

## 反例 4：模板硬塞到不该用的文章

**症状：** 给 200 字符的 commit message / 单行 API 签名 / changelog 套 7 段模板。

**真实案例：**
- ❌ 给 commit message "fix: 修复登录页溢出" 套 02 模板（变成 5000 字怪物）
- ❌ 给 API 文档 `function foo(x: number): boolean` 套 02 模板
- ❌ 给一行 changelog `- v1.2.0: 新增导出功能` 套 02 模板

**正确做法：** 看 SKILL.md "不适用场景" 判定表：

| 场景 | 正确做法 |
|------|----------|
| 原文 < 500 字符 | 不升级，原样保留 |
| API 参考文档 | 保留原结构，只补"术语 + 说白了" |
| 1000 字内但用户没要求简短 | 用 5 段轻量版（见 upgrade-template.md） |
| 1000+ 字符、有完整章节 | 用 7 段完整版 |

## 反例 5：专业小技巧凑不够硬凑

**症状：** 写不出 4 条真实技巧，就把同一条改个说法重写 4 遍。

**真实案例：**
- ❌ "1. 写测试很重要。2. 测试要写好。3. 测试要覆盖边界。4. 写测试要尽早。"（4 条都是"写测试"换皮）
- ❌ "1. 要 review。2. 要认真 review。3. 要及时 review。4. 要 review 重点。"（同上）

**正确做法：** 质量 > 数量。

- ✅ 写不出 4 条就只写 2-3 条真实的。
- ✅ 没真实技巧就跳过这个段，不要硬凑。
- ✅ "宁缺毋滥"原则：2 条真货比 4 条废话强 10 倍。

## 反例 6：占位符没替换干净

**症状：** 升级版里还残留 `<your-token>` / `<placeholder>` / `TODO` 这种占位符。

**真实案例：**
- ❌ `"GITHUB_TOKEN": "<your-token>"`（在真实配置里）
- ❌ `pnpm test -- <file>`（在命令示例里）
- ❌ `# TODO: 填具体值`（在示例代码里）

**正确做法：** 占位符只在"反例"段（演示错误用法）出现，主配置 / 主命令 / 主代码全部用真实值或真实场景描述。

- ✅ `"GITHUB_TOKEN": "ghp_xxxxxxxxxxxxxxxxxxxxxxxxxxxx"`（真实格式示例）
- ✅ `pnpm test -- src/auth/login.test.ts`（真实参数）
- ✅ `# 实际配置：去 https://github.com/settings/tokens 生成`（动作描述代替占位符）

**验证方法：** 跑 `grep '<.*>'` 全文，应该只在反例段出现，主段为 0。

## 反例 7：说"说白了"但不真的说白

**症状：** 加了"说白了："标签，但后面的内容还是抽象 / 术语堆。

**真实案例：**
- ❌ "**说白了：** sandbox 是一个隔离执行环境的机制。"（还是术语）
- ❌ "**说白了：** 异步编程是事件驱动的并发范式。"（还是抽象）
- ❌ "**说白了：** 这是一个 best practice。"（英文也算术语）

**正确做法：** "说白了" 后必须是**真大白话**——人话 + 比喻 + 数字。

- ✅ "**说白了：** sandbox = 物理上把 Codex 锁在某个区域，让它只能动该动的文件 / 命令。AGENTS.md 是'员工手册'（软的）；sandbox 是'门禁系统'（硬的）。"
- ✅ "**说白了：** 异步编程 = 你点外卖不等厨师做完，先去打游戏，饭好了外卖员叫你。比同步（站在厨房等）更省时间。"

**判断标准：** 把"说白了" 后面的内容讲给完全不懂技术的人听，**他听懂了吗**？听不懂 = 没说白。

## 反例 8：升级版破坏了原结构

**症状：** 用户硬要求"章节顺序 / 列表顺序 / 表格行数 0 修改"，但升级版改了。

**真实案例：**
- ❌ 原文 "## 一、二、三" → 升级版改成 "## 故事开场、啥是 X、..."（破坏章节顺序）
- ❌ 原文表格 5 行 → 升级版变成 4 行或 6 行（破坏表格行数）
- ❌ 原文列表 "A、B、C、D" → 升级版加了 E 或删了 B（破坏列表顺序）

**正确做法：** 章节顺序、列表顺序、表格行数 **0 修改**——只能在原结构上**增补润色**。

- ✅ 原文 "## 一、MCP 是什么" → 升级版 "## 一、MCP 是什么（小白 + 专业双达标版）"（仅追加）
- ✅ 原文表格 5 行 → 升级版表格 5 行（行数不变，但内容升级）
- ✅ 原文 "## 常见问题" → 升级版 "## 常见问题（避坑）"（仅追加说明，不破坏结构）

**为啥这条最严：** 用户在原文章上花了时间组织结构，破坏 = 让人找不到对应内容。

## 自查清单（写完升级版后，对照这 8 条）

- [ ] 没保留原文绝对化词（反例 1）
- [ ] 故事开场 ≤ 5 句（反例 2）
- [ ] 检查清单每条都能 30 秒内判断过 / 不过（反例 3）
- [ ] 短文 / API 文档没用 7 段模板硬塞（反例 4）
- [ ] 专业小技巧没硬凑（反例 5）
- [ ] 占位符在主配置 / 主命令里清零（反例 6）
- [ ] "说白了" 后是真大白话（反例 7）
- [ ] 原结构（章节 / 列表 / 表格）0 修改（反例 8）
