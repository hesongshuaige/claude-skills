## 三、优化版规则模板（保留人设 + 补硬约束）

学习类（苏格拉底）通用 7 条：
1. 一次只问 1 个问题
2. 用提问引导我自己想通，**绝对不要直接把答案告诉我**
3. 答错时：严厉点出错在哪，但**绝对不要直接说正确结论**——用反问/类比引导我自己推
4. 答对时：简短肯定 + 追问更深一层
5. 开场先问 1 个探测问题摸底
6. 全程口语化，不用标题/分点/编号
7. 判断掌握后：一句话总结 + 立刻出真实场景应用题考我，不要问"要不要继续"

其他类型优化方向：
- **文案类**补：N条风格各异 + 禁AI腔词表 + 字数上限 + 优惠用占位符 + 转化引导
- **分析类**补：先体检数据 + 每结论附计算依据 + 标信心度 + 数据不足明说不硬编
- **生图类**补：明确"只要背景+留白" + 风格关键词锁质感 + "直接出图不要废话"

## 四、飞书上传流程（lark-cli）

```bash
SPACE=$SKILLUP_SPACE_ID
# 1. 上传 md
FT=$(cat "<md文件>" | lark-cli markdown +create --as user --content - --name "<标题>.md" --format json 2>/dev/null | jq -r '.data.file_token')
# 2. 挂到库根
NT=$(lark-cli wiki +move --as user --obj-type file --obj-token $FT --target-space-id $SPACE --format json 2>/dev/null | jq -r '.data.node_token')
echo "URL=https://my.feishu.cn/wiki/$NT"
# 3. 更新索引（overwrite，file_token 不变）—— ⚠️ 索引内容必须按 §七 的 9类6字段格式，禁用旧课程分类格式
cat "<索引md>" | lark-cli markdown +overwrite --as user --file-token $SKILLUP_INDEX_TOKEN --content - --format json
```

**坑**（踩过，必避）：
- `--file` 拒绝对路径 → 用 `cat | --content -` 走 stdin
- `--name` 必带 `.md` 后缀，否则飞书不渲染
- `wiki +node-get` 用 URL 形式 `--node-token "https://my.feishu.cn/wiki/XXX"`（raw token 会报"--obj-type required"）
- M3 输出混 `<think>` 段：剥 `</think>` 后取正文；max_tokens 给 4096 防 think 吃光
- stdout 混进度行（"Running wiki move..."），jq 提取用 `.data.xxx`

## 七、索引页格式规范（9 类 6 字段 · agent + 人双友好）

> ⚠️ **顶部「🎯 按需求速查」必须用列表格式**（`- 我想干啥 → 【类】`），**不要用表格**——飞书手机端 markdown 表格列宽按内容自适应、不撑满，"去哪个类"列太短会导致整个表只占屏幕左边 1/4。列表每行自然撑满屏宽，手机友好。

索引页 file_token = `$SKILLUP_INDEX_TOKEN`（node=`<运行时 upload.sh 输出>`，已改名【索引】提示词总目录）。**每次入库新提示词后必按本规范更新**（2026-07-21 全库重构后的唯一格式，禁用旧的"按课程分类"）。

### 9 个功能类目（新提示词必归其一）
| 类 | 含义 |
|---|---|
| 写作 | 直接产出能发布的文字（文案/文章/标题/朋友圈）|
| 拆解 | 逆向/对标/克隆已有内容（爆款、风格、骨架）|
| 分析 | 从数据/财务提炼结论 |
| 开发 | 软件/产品/API/数据库/代码 |
| 驾驭 | 控制/对齐/追问/交接 AI 的元技能 |
| 决策 | 拍板/挑刺/找漏洞/判断能不能做 |
| 设计 | 出图/视觉/海报/包装/配色 |
| 学习 | 学概念/精读笔记/视频加工 |
| 框架 | 给 AI 下指令的结构模板（APE/BROKE 等）|

### 每条 6 字段（列表块格式，照填不漏）
```markdown
### 大白话提示词名
- 🔗 [打开文档](https://my.feishu.cn/wiki/<node_token>)
- **干啥**：<一句话，小白能懂，≤25 字>
- **什么时候用**：<典型场景，≤25 字>
- **你给它**：<用户要准备/输入啥，要具体，≤20 字>
- **它给你**：<AI 产出啥，要具体，≤20 字>
- **关键词**：<3-5 个，用 · 分隔>
```

### 命名规则（文件名带【功能】前缀，索引条目标题不带）
- **文件名**：`【功能】大白话名.md`（upload.sh 的标题参数传这个，例 `【分析】把会议纪要整理成带待办`）
- **索引条目标题**：就是 `### 大白话名`（**不带【功能】前缀**，因为条目已挂在对应功能类标题下，再带重复）。例：`### 把会议录音乱稿整理成带待办的纪要`
- **不编号**、场景融入名字、**禁裸用术语**（小白一眼懂）。例：`【驾驭】换一家不同的AI互相核对关键判断`
- 框架类去编号但括号留英文缩写方便查证：`【框架】做啥为啥要啥三段式（A.P.E）`

### 更新流程（入库后）
1. fetch 当前索引：`lark-cli markdown +fetch --as user --file-token $SKILLUP_INDEX_TOKEN --format json | jq -r '.data.content' > /tmp/idx.md`
2. 判断新提示词归属哪类 → 在索引里找到 `## <emoji 类名>` 标题（如 `## ✍️ 写作`），在该类**最后一个 `### 条目` 之后**插入新 6 字段块。
3. overwrite：`cat /tmp/idx.md | lark-cli markdown +overwrite --as user --file-token $SKILLUP_INDEX_TOKEN --content -`
4. 验证：重新 fetch，确认新条目关键词在 + `### ` 条目数比之前 +1。

### 坑（踩过）
- fetch 的 content 在 **`.data.content`**（`--format json` 时），不是顶层 `.content`。
- overwrite 用 `cat | --content -`（stdin）实测可行；`--content @file` 会报错要求配 `--file` 参数。
- overwrite 偶发返回 ok 但没写入——**必须 fetch 验证**关键词，别信返回值。

## 八、提示词质量评审框架（用 MiniMax-M3 跑，独立评审所有交付物）

```
你是极其挑剔、以毒舌著称的提示词工程首席评审官，专挑致命伤。评审一段提示词
（或场景实跑输出）是否达到可交付水平（无致命硬伤 + 实跑有用，不打分）。禁止任何恭维/鼓励/安慰
（"总体不错""方向是对的""加油"全部禁止）。

【你会拿到】
- 被评审提示词：原文
- 提示词目标：它原本要解决什么问题、达到什么效果
- 场景实跑输出（仅场景/举一反三模式给）：提示词在某场景下 M3 实跑的产出原文

【评审流程】
① 复述靶子：3 条以内复述【提示词目标】，证明抓对了。看不出就直说"看不出来，
   无法评审"，不要编。

② 找致命硬伤（最多 3 个；**不打分**，只找致命问题）：
   重点查：编数据 / AI 腔 / 跑题 / 不给答案 / 占位符不清 / 输出结构不稳 / 信息不够硬编 / 小白看不懂要填啥 / 没真解决目标问题

③ 撕致命漏洞（最多 3 个），每个按格式：
   - 漏洞是什么：一句话点要害
   - 为什么致命：不补救会怎样，给具体失败场景或量化损失（"会有风险"不算）
   - 犀利补救：一条可立刻执行的动作（"加强 XX""持续优化"这种废话不算）
   - 信心度：高/中/低

④ 总结（**不打总分**，只给判断）：
   - 致命硬伤：列出找到的（若有）/ 写"无致命硬伤"
   - 实跑输出（场景模式）：有没有解决场景问题（是/否 + 一句理由）
   - 判定：✅可交付（无致命硬伤 + 实跑有用）/ ❌需改（有致命硬伤，按补丁改到收敛）
   - 注：本框架是**找问题工具不是绝对裁判**——**绝不算总分**（视角漂移会震荡），只看「有无致命硬伤 + 实跑有没有用」（详见 §十分型规则）
   - 如果只能改一条：先改哪个，为什么
   - 信息/数据不足：直接说"信息不够，无法判断"，绝不编数字撑结论

【场景/举一反三模式】
评使用场景或举一反三时：拿【提示词】+【该场景典型输入】让 M3 实跑产出输出，
你（切评审角色）评这个输出——重点看：有没有真解决该场景的问题（不是空话/套话糊弄）。同时判断"这场景适不适合用这提示词"，
不适合就指出并建议换场景。
```

**用途**：找致命硬伤的工具，**不打总分**。只看「有没有致命硬伤」+「实跑输出有没有用」。

**⚠️ 评审框架用途边界（2026-07-21 实证）**：
- ✅ **作"找漏洞驱动改进"工具：优秀**——每轮精准挑真问题、会升级视角（工程→防漏→商用留存）。
- ⚠️ **作"绝对分数裁判"：有局限**——评审视角漂移、分数震荡（实证 40→66→84→70→80→89→82 不收敛），**所以本框架已删打分逻辑**。
- **正确用法**：只找致命硬伤 + 看实跑输出有没有用，**绝不算总分**（详见 §十分型规则）。

## 九、使用场景板块模板（3-5 个，层 2 验证对象）

文档"使用场景"块写 **3-5 个最常见真实场景**（不贪多，深度优先），每个按模板：

```
**场景 N：<一句话场景名>**
- 什么情况用：<具体情境，深度到"什么时点、遇到什么问题">
- 典型输入：<你给它什么>
- 预期输出：<它给你什么>
- 注意事项：<这个场景的坑/需要微调哪里>
```

**与举一反三的区别（防内容撞车）**：
- **使用场景** = 本提示词**何时用**（不改提示词，原提示词 + 不同情境输入）
- **举一反三** = **衍生新提示词**（换人设/换领域，如董事会拷问 → 私募投决版/小红书种草版）

两者都验证（层 2、层 3），但验证对象不同：使用场景验原提示词的适用面，举一反三验衍生提示词的效果。

## 十、分型验证规则（2026-07-21 实证校准·结果导向）

**先分型，再按型验证。** 提示词复杂度决定能不能用单条 prompt 做好（实证：简单类一跑就出好结果，复杂类 6 版仍卡壳）。

### A 类·简单类（单轮·输入→输出清晰）= skillup 主力
**适用**：写作 / 拆解 / 分析 / 设计 / 学习 / 框架（12 框架）。
**验证**：① 评审框架（§八）找致命硬伤，改到**收敛**（找不出致命）；② **实跑 3 个真实场景**（贴合新媒体/私募主业），看输出**有没有用**（能解决场景问题、无 AI 腔、无编造）。两者过 = 合格。**不卡绝对分数**（评审视角漂移会震荡不收敛）。

### B 类·复杂类（多轮·诊断型）= 不适合单条 prompt
**适用**：评审 / 魔鬼代言人 / 尽调 / 投决（需多轮交互+状态+分支）。
**处理**：① 先砍成**单轮简化版**——去硬停止/多轮/C 分支罢工，信息不够就老实说"给方向性判断"+给方向（不甩占位符）；② 简化版按 A 类标准验；③ 简化不掉（单轮版仍跑不顺）→ **劝退**：标注"超出单条 prompt 能力，建议做 agent/独立工具"，交用户定，不强做。

### 判例（实证，供分型参考）
- ✅ **朋友圈文案（A 类·简单）**：单轮输入产品→输出 3 条文案。实跑 3 场景（课程发售/基金募资 LP/AI 工具卖货），9 条全好用（能收钱、无 AI 腔、优惠用占位符不编）。**A 类范本，一跑就出好结果。**
- ❌ **董事会拷问（B 类·复杂）**：需多轮+硬停止+状态。v5 简化 6 版震荡（40→66→84→70→80→89→82），层 2/3 实跑 **0/11**（硬停止瘫痪、占位符泥潭、C 分支罢工）。**B 类不适合单条 prompt 的实证。**

### 评审框架（§八）用途 = 找问题工具，不是绝对裁判
用它找致命硬伤（收敛即可），**别死磕绝对分**。视角漂移轨迹：工程→防漏→商用留存，分数震荡不收敛。

### 成本预期
A 类约 5-8 次 M3（评审找问题 + 3 场景实跑）。B 类若尝试简化，约 15-20 次；劝退则 0。
